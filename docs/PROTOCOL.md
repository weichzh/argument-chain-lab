# 完整政策框架问卷协议

本协议把一次评测定义为用户逐题判断完整政策方案的过程。形式结构负责判断下一题是否有意义，前台不要求用户学习内部术语。

## 1. 单项政策流程

对每个完整原方案 `P₀`：

1. 依次显示政策情景、只读固定条件和完整方案的所有关键安排。
2. 在上述信息之后，询问用户认为 `P₀`“应当”“不应当”还是“不确定”。
3. “应当”直接进入支持 `P₀` 的理由；“不确定”结束本题，不生成反对理由。
4. “不应当”按成本非递减的顺序，一次显示一个完整修改方案 `Pᵢ`。
5. 若用户接受 `Pᵢ`，同时记录 `Reject(P₀)` 与 `Accept(Pᵢ)`，将二者差异定位为当前反对点并停止默认诊断。
6. 若用户拒绝所有已列出的修改，只记录这些修改未能改变判断，并提供面向原方案的理由选项；不推断用户拒绝所有可能设计。
7. 用户选择主要理由后，逐项核对其题设假设，再判断这些假设是否足以构成一项可撤销理由。
8. 用户可以继续追问更深理由，或把当前规范命题作为本轮暂时停止点。
9. 停止点经过一次包含具体人物、行为或制度情景的相似案例检查，再核对一条与当前争点对齐的相反理由；题库缺少具体案例时必须标记为未检查，不能生成通用模板。
10. 当前政策结束后，用户进入下一题或查看阶段结果。

“有条件接受”只能由下式派生，不能成为初始选项：

```text
Reject(P₀) + Accept(Pᵢ) + Pᵢ = Revise(P₀, Δ)
→ ConditionalAcceptance(P₀, Δ)
```

`Δ` 只是已测试方案中第一个足以改变判断的修改，不表示世界上唯一或绝对最小的条件。

## 2. 理由路径

理由路径始终指向一个明确的完整方案判断或局部反对点：

```text
当前判断
← 题设假设
← 判断依据
← 更深理由
← 本轮暂时停止点
```

默认 8 项核心政策的每个支持、诊断和最终反对叶至少提供两条策展理由。5 项附加精度题的每个局部诊断叶至少提供一条已策展理由。每个非停止判断依据至少有一条更深路径。用户继续追问超过题库深度，或题库没有合适理由时，统一进入自定义理由，不显示空白页面。

自定义理由可以直接保存，也可以交给用户配置的 AI 整理。AI 只能返回等待确认的结构化候选，不能改写当前判断、替用户接受前提或签发正式证书。用户确认后的候选标记为 `custom_unverified`。

## 3. 回看与依赖失效

每次回答前保存状态快照。用户选择“上一题”或从“查看已答”修改早期回答时：

1. 恢复到该回答之前；
2. 丢弃所有由它生成的后续回答；
3. 保留其他政策结果；
4. 从新路径继续，不把旧答案强行套入新问题。

重新回答一项已经完成的政策时，只清除该政策的旧结果。刷新、返回主页或打开题目列表不会丢失当前结构化进度。

## 4. 跳过与中止

根问题允许跳过。跳过只记录“已跳过”，不伪造未解决判断或理由。用户可以随时中止并查看结果；进行中的当前题仍保存在浏览器中，随后可以继续。

题目列表不提供开始前多选或模式选择，只列出 8 项核心政策。用户可以从任意一道开始，之后按列表顺序继续。5 项精度政策不形成第二套问卷；只有用户在娱乐结果中主动提高精度时，matcher 才从未回答项中推荐一题并把它追加到同一状态流。

## 5. 结果

默认结果只显示：

- 对原方案的判断；
- 是否接受一个修改后的完整方案；
- 使判断改变的具体差异；
- 主要理由和更深理由；
- 相反理由及其影响；
- 自定义理由尚未经过正式题库校验的提示。

默认界面不显示内部逻辑记号、证书哈希或形式状态统计。完整理由路径只在“查看详细推理记录”中展开。结果描述本轮公开承诺，不推断政治身份、人格或概率。

娱乐结果默认关闭。用户主动启用后，客户端才延迟读取独立 benchmark，并按以下边界展示：

- 始终先显示用户自己的论证型和 16 位分享指纹；
- 政策覆盖不足 40% 时不显示单一历史名称；
- 信息较浅时显示候选组，不强行唯一化；
- 信息充分时显示最近参考、替代项、第一与第二名差距、来源状态、决定性相似和实质差异；
- 75 个参考名称都以中文和原文并列显示，23 个尚待独立整理的名称只能进入候选组；
- 政策覆盖、论证深度和综合证据覆盖分别显示，不合并成身份“置信度”；
- 极权、法西斯、种族主义或高威权原型只使用中性文字，不使用庆祝式呈现；
- matcher 每次最多推荐一项尚未回答的精度题。

娱乐相似度只表示当前 benchmark 中的论证路径接近，不是身份概率。未回答和跳过项目降低覆盖度，不计为不一致；参考名称不得写回正式题库或用户的政策结果。

## 6. 旧版迁移

1.0、1.1 与 1.2 的 8 项核心政策、完整框架和理由 ID 兼容，1.0 与 1.1 结构化进度可以保留并继续使用 1.2 模型。

0.9 会话中的初始 `conditional`、组件回答和包内取舍没有保存一个被用户明确接受的完整框架。迁移器因此只做只读归档：

- 新版 `policyResults` 为空；
- 旧政策记录、理由链、冲突和题库缺口保存在 `legacyArchive`；
- 旧记录可以查看和导出；
- 旧判断不参与新版结果、匹配或公开贡献。

产品不提供继续旧版问卷的并行入口。
